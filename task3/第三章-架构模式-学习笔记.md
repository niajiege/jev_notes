## 一、这一章的位置

第二章解决的是「问什么」：怎么把判断拆成 state 和类型化问题，以及概率、置信度、校准分别是什么意思。

第三章换了一个问题：**一个已经拿到概率的判断，怎么进入程序**。

课程给的边界很清楚：

> 模型提供语义信号，代码负责权限、规则、顺序和副作用。

这句话反过来读更有用：模型**不**负责决定「能不能执行」「先做哪一步」「失败了怎么办」。它只回答「属于哪一类、有多大可能」，剩下的都该是代码。

四种模式就是这条边界上的四种接法：

| 模式 | 目标 | 常见代价或失败方式 |
|---|---|---|
| 推测性扇出 | 一次提出多个可能需要的问题，减少后续往返 | 多算暂时用不到的问题；请求更大，不保证延迟不变 |
| 置信度门控 | 高风险或不确定的样本转人工、重试或升级 | 覆盖率下降；置信度不能替代风险标签或真实验证 |
| 复合评分 | 保留多个维度，让业务代码按岗位或目标组合 | 权重表达的是业务取舍；尺度不一致时加权没有清晰含义 |
| 意图路由 | 把输入送往匹配的处理器，避开无关路径 | 路由器本身会错；需要未知类、fallback 和监控 |

连起来是一条链：

**state → 扇出（提多个候选问题）→ 类型化判断与分布 → 门控（未知或高风险就拒绝/澄清/转人工）→ 代码组合维度与权重 → 意图路由 → 受控处理器**

Notebook 的四个练习正好对应这条链的四个环节。

## 二、推测性扇出

### 2.1 一条工单，五个问题

state 是一条写得比较杂的支持工单（扣款、退款、功能问题混着说）。一次请求里问五件事：

| 问题 | 原语 | 选项 / 量表 |
|---|---|---|
| `category` | `Choice` | bug_report / billing / feature_request / account |
| `bug_severity` | `Score` | 外观问题 → 功能受损 → 阻塞性问题 |
| `has_reproducible_steps` | `Noul` | 是否描述了复现步骤 |
| `refund_requested` | `Noul` | 是否明确要求退款或补偿 |
| `frustration` | `Score` | 平静 → 有些沮丧 → 非常愤怒 |

这一次调用（623 input tokens）拿到的答案：

| 问题 | 结果 | 置信度 |
|---|---|---|
| `category` | `billing`（`billing` 0.97 / `bug_report` 0.02 / `account` 0.01） | 0.96 |
| `bug_severity` | `score = 1.61` | **0.41** |
| `has_reproducible_steps` | `noul = 0.12` | 无 |
| `refund_requested` | `noul = 0.17` | 无 |
| `frustration` | `score = 1.02` | 0.97 |

### 2.2 实测：批量 vs 逐条

同样的 state、同样的五个问题，换个问法：

| 组 | 往返次数 | 耗时 | input tokens |
|---|---|---|---|
| A：1 次请求带 5 个问题 | 1 | 0.24 s | 623 |
| B：5 次请求每次 1 个问题 | 5 | 1.12 s | 1939 |

**逐条是批量的 4.6 倍耗时、3.1 倍 token。**

token 差三倍的原因不难理解：state 要跟着每次请求重复发送，逐条等于把同一份工单抄了五遍。口径是 `input_tokens`（扣费口径）。

不过这两个数字只能当**当次的网络快照**看，不能当性能承诺。课程在 README 里也提醒过：批量是不是更快更便宜，取决于输入长度、服务端实现、网络和调用方式，要实测。我这次测到的 4.6 倍里，有多少是往返开销、有多少是服务端排队，我没有办法拆开。

### 2.3 投机的兑现：只取当前分支要用的

扇出的代价是「问了可能用不上的问题」。这一节的代码演示了怎么把代价控制住——按分支消费：

```
类别 = billing（confidence=0.96）
→ 转账单组；用户明确要求退款 = False（noul=0.17）
挫败度评分 1.02（≥1.5 时可插队人工队列）——任何分支都可用
```

这条 `billing` 分支实际用到了三个答案：`category` 定分支、`refund_requested` 决定要不要走退款、`frustration` 决定要不要插队。**`bug_severity` 和 `has_reproducible_steps` 在这条路径上完全没用上**，但它们的 token 已经付过了。

所以推测性扇出的真实权衡是：**用「可能浪费的问题」换「确定省下的往返」**。值不值取决于分支分布——如果 90% 的工单都走 billing，那多问的那两问就是稳定的浪费；如果分支很分散，多问反而省事。这一点我没有真实流量，无法验证。

另外注意 `bug_severity` 的置信度只有 0.41：工单里没有明确说严重程度时，分数照样给出来了（1.61），但这个分数不该被单独拿去做决策。

## 三、置信度门控路由

### 3.1 阈值跟着风险走

这一节用的是语音银行的例子：同一套意图分类，四种指令，**门槛不是全局的一个数**。

| 条件 | 动作 | 理由 |
|---|---|---|
| `confidence < 0.6`（任何意图） | 转人工 | 模型真的不确定，别猜 |
| `check_balance`，≥ 0.6 | 直接执行 | 低风险：错了不过是再听一遍余额 |
| `approve_transfer`，0.6 – 0.85 | 请用户确认 | 高风险 + 中等置信度，先核实 |
| `approve_transfer`，> 0.85 | 自动批准 | 高风险 + 高置信度 |

### 3.2 为什么不能只挑最大概率

这一节背后其实是一条决策理论：**如果不同错误的业务代价不同，选最大概率类别不一定是最合适的动作。**

给定分布 `p(y|x)` 和损失 `L(a, y)`，应该选让后验期望损失最小的动作：

```
a* = argmin_a  Σ_y p(y|x) · L(a, y)
```

课程里给了一个玩具例子，损失单位是任意的，只用来演算：

- 模型判断「有紧急问题」的概率是 **0.20**，也就是最大概率类别是「不紧急」；
- 自动关闭的损失：问题确实紧急时 100，不紧急时 0 → 期望损失 `0.20 × 100 + 0.80 × 0 = 20`；
- 转人工的损失：不管紧急不紧急都记 4。

**20 > 4，所以该转人工**，尽管最大概率的类别是「不紧急」。

这就是门控存在的理由：**动作的价值不由概率决定，由损失决定。** 只有当动作就是预测类别、且损失是 0–1 损失时，这个规则才退化成「选最大概率」。

### 3.3 四条指令的实测

| 指令 | 意图 | confidence | 决策 |
|---|---|---|---|
| 帮我查一下储蓄卡余额 | `check_balance` | 1.00 | 💰 直接播报余额（低风险，0.6 足够） |
| 请批准那笔待确认的转账 | `approve_transfer` | 1.00 | ✅ 自动批准转账（高风险 + 高置信度） |
| 来点爵士乐吧 | `other` | 1.00 | 📞 转人工客服（其他意图） |
| 行，就按你说的办 | `other` | **0.51** | 📞 转人工客服（置信度过低） |

两个观察：

1. **0.6–0.85 这个「请用户确认」区间一次都没命中。** 两条能解析的指令都在 1.00，唯一落进低置信区的是「行，就按你说的办」——它是指代不明，不是「有点拿不准」。Notebook 自己也写了这个发现：模型对可解析的意图极其笃定（含「转账」字样的含糊表达也都在 0.9 以上），解析不出的则落到低置信。这跟我在第二章观察到的「置信度两极分化」是同一件事：**中间档是留给模型行为变化的安全网，代码路径要备好，哪怕日常走的是另外三条。**
2. **「来点爵士乐吧」以 confidence 1.00 被归到 `other`。** 这是很有用的一课：它的高置信度说明的是「我确定这不是银行业务」，不是「我确定该怎么做」。最后仍然转人工——**高置信度不等于动作正确**，门控看的是「意图 + 置信度」的组合，不是置信度一个数。


## 四、复合评分

### 4.1 四个维度，量表各管一段

三位候选人，四道 `Score` 题，每道都是 0–4 的五级量表：

| 维度 | 量表从哪到哪 |
|---|---|
| `python_depth` | 未提及 Python → 深厚功底（架构、性能优化、类库建设） |
| `team_leadership` | 未提及管理 → 管理过多个团队或整个工程部门 |
| `system_design` | 未提及架构 → 跨多个领域设计过大规模系统 |
| `generalist` | 只深耕一个领域 → 在 4 个以上不同领域交付过成果 |

实测的原始分（0–4，概率加权期望值）：

| 候选人 | python_depth | team_leadership | system_design | generalist |
|---|---|---|---|---|
| 张伟（资深 IC 型） | 4.00 | 1.00 | 3.18 | 1.59 |
| 李强（管理者型） | 1.28 | 3.99 | 3.45 | 1.13 |
| 王雪（均衡成长型） | 3.00 | 1.18 | 1.79 | 1.92 |

### 4.2 换一个岗位 = 换一行权重

同一批分数，两套岗位权重：

| 岗位 | python_depth | team_leadership | system_design | generalist |
|---|---|---|---|---|
| 资深 IC | 0.40 | 0.10 | 0.40 | 0.10 |
| 工程经理 | 0.15 | 0.40 | 0.20 | 0.25 |

先把每项除以 4 归一到 0–1，再按权重加权求和：

| 候选人 | 『资深 IC』 | 『工程经理』 |
|---|---|---|
| 张伟 | **0.783** | 0.508 |
| 李强 | 0.601 | **0.690** |
| 王雪 | 0.557 | 0.440 |

排名：

- 『资深 IC』：张伟 > 李强 > 王雪
- 『工程经理』：李强 > 张伟 > 王雪

再加一个『首席架构师』岗位（架构占 60%），结果仍是 **张伟 > 李强 > 王雪**。

这张表最直观的地方是：**模型给出的四个分数一次都没变，变的只是我写的那行权重，排名就翻了。** 权重不是模型的事实，是业务的取舍——「这个岗位更看重带人还是更看重写代码」这件事，模型没有立场。

归一化那一步也不能省：四个维度虽然都是 0–4，但只要以后有一个量表变成 0–5，不归一就直接加权，那一项就被放大了。我在第二章的分维度加权里踩过同类的坑。

## 五、意图路由

### 5.1 两个问题：是什么 + 多复杂

一次请求问两件事：`intent`（四类 `Choice`）+ `complexity`（三级 `Score`）。路由函数长这样：

```python
def route(msg, answers):
    intent, complexity = answers["intent"], answers["complexity"]

    if intent.confidence < 0.5:
        return human_agent(msg)
    if intent.choice == "order_status":
        return deterministic_order_lookup(msg)
    if intent.choice == "product_question":
        return specialist_llm("产品", msg)
    if intent.choice == "return_exchange":
        return specialist_llm("退货", msg)

    # complaint：复杂度高于"多步流程"或置信度不足时升级人工
    if complexity.score > 1 or complexity.confidence < 0.5:
        return human_agent(msg)
    return specialist_llm("投诉处理", msg)
```

注意 `order_status` 走的是**确定性代码查库**，不是 LLM 生成——「订单到哪了」这种问题有唯一答案，不该让模型编。

### 5.2 五条消息的实测

| 消息 | intent | conf | complexity | 去向 |
|---|---|---|---|---|
| 我的订单 #12345 到哪了？三天前就显示发货了。 | `order_status` | 0.99 | 0.17 | 确定性代码查库 |
| X 型号的意式咖啡机附赠不锈钢拉花缸吗？ | `product_question` | 1.00 | 0.01 | 产品专家 LLM |
| 那双跑鞋我想退货，偏小半码。 | `return_exchange` | 1.00 | 0.07 | 退货专家 LLM |
| 这是第三次坏了……我要全额退款，让你们经理给我回电话…… | `complaint` | 0.95 | **1.98** | 人工客服 |
| 。。。 | `product_question` | **0.23** | 0.41 | 人工客服 |

三条兜底路径这次都起作用了：

- **意图置信度低** → 「。。。」被归到 `product_question`，但 conf 只有 0.23，直接进人工。这就是不给「未知」选项时的退路。
- **意图清楚但事情复杂** → 投诉那条 conf 0.95（很确定是投诉），但 complexity 1.98 超过了「多步流程」这一级，仍然升级人工。**确定是什么，不等于能自动处理**，路由看了两个维度。
- 第一条走了确定性代码，返回的是「订单 #12345：已到达本地配送站」——这句话不是模型写的。

## 六、小结：四种模式怎么串

| 环节 | 回答的问题 | 谁来定 |
|---|---|---|
| 推测性扇出 | 这次判断可能要用到哪些信息？ | 我（问题集） |
| 置信度门控 | 这个结果够不够格自动执行？ | 我（阈值 + 损失） |
| 复合评分 | 多个维度怎么合成一个业务排序？ | 我（权重） |
| 意图路由 | 这条输入该交给谁？ | 我（分支表） |

模型在这条链上只做一件事：给出类型化的值和概率。四种模式全都是**代码怎么用它**的问题。


1. 固定规则、授权、金额限制、安全联锁放在代码里，不靠模型记忆。
2. 遇到无证据、低置信或超出选项范围的结果，要有拒绝或人工升级路径。
3. 多维分数先定义单位、尺度和权重来源；权重是业务政策，不是模型事实。
4. 对自动动作记录输入版本、判断结果、使用的规则和动作结果，便于复盘。

## 七、遗留问题

1. **阈值怎么定（0.6 / 0.85 / 0.5）还是靠试。** 这三个数是示例值，我手上没有标注样本，画不出 risk–coverage 曲线，也不知道换个业务该往哪边挪。
2. **中间档到底还有没有用。** 第二章里 confidence 几乎只在两极出现，这章的四条指令同样是 1.00 和 0.51，0.6–0.85 一次没命中。安全网该留，但它值不值得占一条代码路径，要看真实流量。
3. **推测性扇出的浪费没法量化。** 这次 5 问里有 2 问没用上；如果线上分支更集中，浪费比例会更高。要不要按分支频率裁剪问题集，我还没有方法。
4. **权重谁定、怎么申诉。** 复合评分把「岗位看重什么」变成了一行数字，但这行数字是招聘方定的，候选人看不到，也没有复核机制。
5. **没有 `unknown` 类。** 这次靠 conf 0.23 把「。。。」兜住了；但如果出现一个真正的新意图、模型又给了高置信度，路由会把它硬塞进最接近的已知类。课程要求的「未知意图 + fallback + 监控」我只做了 fallback，监控还没有。
6. **单次测量不能当性能结论。** 4.6 倍耗时、3.1 倍 token 都是当次快照，要比较不同调用方式，需要多轮重复取分布。
